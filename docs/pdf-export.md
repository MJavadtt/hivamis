# خروجی PDF اسناد — PDF document export

## چرا موتور مرورگر

فارسی به شکل‌دهی متنی وابسته به موقعیت حرف (contextual shaping) و چیدمان دوجهته (bidi) نیاز دارد.
هیچ کتابخانه‌ی تولید PDF مبتنی بر جاوااسکریپت این دو را به‌درستی انجام نمی‌دهد؛ خروجی آن‌ها حروف
جدا و وارونه است. بنابراین سند در یک موتور مرورگر واقعی (Chromium via Playwright) صفحه‌بندی و
سپس چاپ می‌شود. این تصمیم در `docs/decisions.md` ثبت شده است.

قلم Vazirmatn به‌صورت base64 داخل خود سند جاسازی می‌شود، بنابراین خروجی روی سروری که هیچ قلم
فارسی نصب ندارد نیز دقیقاً یکسان است.

## راه‌اندازی

موتور به یک باینری Chromium نیاز دارد. ترتیب جست‌وجو:

1. متغیر محیطی `PDF_BROWSER_PATH` (اولویت مطلق)
2. کش Playwright — `~/Library/Caches/ms-playwright` در macOS، `~/.cache/ms-playwright` در لینوکس
3. مرورگر سیستمی: Google Chrome، chromium، chromium-browser، google-chrome

### نصب مرورگر

```bash
pnpm --filter @hiva/api exec playwright install chromium
```

### در Docker

`infrastructure/docker/Dockerfile.api` این کار را انجام می‌دهد و نیازی به تغییر نیست:

```dockerfile
FROM node:22-bookworm-slim AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends \
      chromium ca-certificates openssl tini curl \
 && rm -rf /var/lib/apt/lists/*
ENV PDF_BROWSER_PATH=/usr/bin/chromium
```

هر دو مرحلهٔ build و runtime روی Debian هستند، نه Alpine — به دو دلیل:

1. Playwright رسماً Debian و Ubuntu را پشتیبانی می‌کند؛ Alpine در فهرست پشتیبانی‌شده نیست.
2. `@node-rs/argon2` و موتور Prisma باینری وابسته به پلتفرم دارند. ساخت روی musl و اجرا روی
   glibc (یا برعکس) کانتینری می‌سازد که هنگام راه‌اندازی شکست می‌خورد؛ بنابراین هر دو مرحله
   باید یک libc مشترک داشته باشند.

نیازی به نصب قلم فارسی روی ایمیج نیست؛ `renderer.ts` وزیرمتن را به‌صورت base64 داخل هر سند
جاسازی می‌کند، پس خروجی روی میزبانی بدون هیچ قلم فارسی هم یکسان است. بستهٔ `fonts-liberation`
لازم نیست.

بررسی اینکه مرورگر در ایمیج کار می‌کند:

```bash
docker run --rm --entrypoint sh hiva-api:latest -c '$PDF_BROWSER_PATH --version'
```

## بررسی سلامت

```bash
curl -s localhost:4000/health/ready
# {"status":"ready","database":"up","demoAccounts":0,"pdf":"up"}
```

فیلد `pdf` وضعیت موتور رندر را گزارش می‌کند («up» یا «unavailable») و هر ۶۰ ثانیه cache می‌شود،
چون راه‌اندازی Chromium گران است و probe آمادگی مکرر اجرا می‌شود.

این فیلد **مسدودکننده نیست**: نبودِ مرورگر سرویس را not-ready نمی‌کند. طبق ADR-014 نبودِ موتور
PDF فقط مسیرهای `/pdf/*` را با ۵۰۳ از کار می‌اندازد و بقیه پلتفرم کار می‌کند، بنابراین نباید
باعث شود ارکستراتور کانتینر را restart کند. برای هشدار، روی مقدار `unavailable` alert بگذارید.

**سند مالی روی فرم شرکت (ADR-125).** سندی که فروشنده (هیوا یا خط تیره) دارد، روی فرم Excel خود آن شرکت
چاپ می‌شود: PDF از همان کارپوشه‌ای کشیده می‌شود که `GET /api/v1/invoices/:id/workbook` می‌دهد — افقی، با
حاشیهٔ ۶ میلی‌متر و بی سرصفحه و پاصفحه، با قلم Vazirmatn. سند پیش از این فرم‌ها چیدمان عمومی را نگه می‌دارد.

## ترتیب دسترسی — Access order

خروجی گرفتن یک عمل «خواندن» است. بنابراین:

**۱. همان مجوزی که برای خواندن رکورد لازم است، برای خروجی هم لازم است.**
PDF هرگز مسیر دور زدن مدل دسترسی نیست. مجوز در `apps/api/src/pdf/access.ts` تعریف و در
`routes/pdf.ts` پیش از تولید سند بررسی می‌شود.

**۲. علاوه بر آن، حذف در سطح فیلد اعمال می‌شود.** دو قاعده‌ی Doc_H روی کاغذ هم باقی می‌مانند:

- **بند ۱۲ «مدیریت مالی پروژه»** — واحد اجرایی قیمت تمام‌شده‌ی خود را اعلام می‌کند و آن را می‌بیند،
  اما قیمت فروش و حاشیه سود برای او پنهان است. فروش برعکس: قیمت را ارائه می‌کند اما قیمت
  تمام‌شده‌ی داخلی را نمی‌بیند.
- **بند ۲ «تفکیک Sales و Account»** — دو حلقه در آنچه هر طرف می‌خواند جدا می‌مانند.

| نقش | قیمت تمام‌شده | قیمت فروش / حاشیه | اطلاعات مالی |
|---|---|---|---|
| اکانت | ✓ | ✓ | ✓ |
| مالی | ✓ | ✓ | ✓ |
| مدیریت (مدیرعامل / قائم‌مقام) | ✓ | ✓ | ✓ |
| واحد اجرایی (استراتژی، خلاقیت، رسانه، دیجیتال) | ✓ | ✗ | ✗ |
| فروش | ✗ | ✓ فقط پس از تأیید QC نهایی | ✗ |
| حقوقی | ✗ | ✗ | ✗ |

**قاعده‌ی زمانی فروش:** پیش از عبور پروپوزال از QC نهایی، قیمت هنوز داخلی است و برای فروش پنهان
می‌ماند. پس از تأیید (مرحله F سند «الگوریتم جامع») فروش برای ارائه به مشتری به آن نیاز دارد و
عدد نمایش داده می‌شود.

**۳. فیلد حذف‌شده حذف نمی‌شود، بلکه «محرمانه — خارج از سطح دسترسی» چاپ می‌شود**، تا خواننده
بتواند «خالی» را از «پنهان‌شده» تشخیص دهد.

**۴. هر خروجی در گزارش حسابرسی ثبت می‌شود** با فهرست بخش‌های حذف‌شده:

```sql
SELECT "createdAt", "actorId", reason, after
FROM audit_events
WHERE action = 'EXPORT' AND "entityId" = '<id>'
ORDER BY "createdAt" DESC;
```

`GET /api/v1/pdf/:kind/:id/exports` (نیازمند `admin.audit`) همین را از طریق API برمی‌گرداند —
یعنی می‌توان دید چه کسی نسخه گرفته و دقیقاً چه نسخه‌ای دریافت کرده است.

## امنیت

- صفحه با شبکه‌ی **غیرفعال** رندر می‌شود (`offline: true` و مسدودسازی همه‌ی درخواست‌ها به‌جز
  `data:`)، بنابراین مقدار مخربی که داخل یک رکورد ذخیره شده باشد نمی‌تواند از میزبان رندر
  درخواست خروجی ایجاد کند (SSRF).
- جاوااسکریپت در صفحه‌ی رندر غیرفعال است.
- تمام مقادیر پیش از درج در HTML با `esc()` فرار داده می‌شوند.
- پاسخ با `Content-Disposition: attachment` و `X-Content-Type-Options: nosniff` ارسال می‌شود.
- `Cache-Control: no-store` — سند ممکن است حاوی اطلاعات مالی باشد.
- دامنه‌ی سازمان همیشه بررسی می‌شود؛ رکورد سازمان دیگر با ۴۰۴ پاسخ داده می‌شود.

## کارایی

اولین درخواست مرورگر را راه‌اندازی می‌کند (~۱ تا ۴ ثانیه). نمونه‌ی مرورگر بین درخواست‌ها
بازاستفاده می‌شود و هر سند در یک context جداگانه رندر می‌شود؛ درخواست‌های بعدی حدود ۳۰۰ میلی‌ثانیه
طول می‌کشند. برای اسناد بسیار بزرگ (گزارش مدیریتی با پرتفوی وسیع) خروجی به ۶۰ ردیف اول محدود شده
است.

# بسته کامل اسناد — bundled export

بیشتر اسناد این سازمان تنها نیستند: فرم‌های Doc_H با ۱۴۵ ارجاع (`entityRef`) به یکدیگر و به
رکوردهای سامانه اشاره می‌کنند و ۷۶ فرم فیلد پیوست فایل دارند. بنابراین علاوه بر خروجی تک‌سند،
می‌توان یک «بسته» گرفت: سند اصلی به‌همراه هر چیزی که به آن پیوست است، در یک PDF واحد.

## کشف پیوست‌ها

```
GET /api/v1/pdf/:kind/:id/attachments
```

پیوست‌ها در سه دسته کشف می‌شوند:

1. **ارجاعات** — فیلدهای `entityRef` خودِ فرم دنبال می‌شوند (فرم → پروژه، پروپوزال، قرارداد و…).
2. **رکوردهای فرزند** — مثلاً یک پروژه: بریف، پروپوزال، سفارش‌های کار، خروجی‌ها، QC، اصلاحیه‌ها،
   درخواست‌های تغییر، قرارداد، فاکتور، جلسات و گزارش‌های وضعیت.
3. **فایل‌های بارگذاری‌شده** — رکوردهای `documents` که به آن موجودیت وصل‌اند.

پاسخ گروه‌بندی‌شده است و هر مورد یک `defaultSelected` دارد؛ اسناد اصلی مسیر (بریف، پروپوزال،
قرارداد، سفارش کار، خروجی) پیش‌فرض تیک‌خورده‌اند و موارد حجیم‌تر (QC، اصلاحیه، صورتجلسه) نه.

## ساخت بسته

```
POST /api/v1/pdf/:kind/:id/bundle
{ "items": [{ "kind": "brief", "id": "…" }], "fileIds": ["…"] }
```

خروجی: یک PDF که با **صفحه فهرست** آغاز می‌شود (شماره، عنوان و نوع هر بخش)، سپس سند اصلی و پس از
آن هر پیوست انتخاب‌شده. هدر `X-Bundle-Sections` تعداد بخش‌ها را برمی‌گرداند.

حداکثر `MAX_BUNDLE_ITEMS` (۴۰) پیوست در هر بسته؛ بیشتر از آن با `BUNDLE_TOO_LARGE` رد می‌شود.

## ترتیب دسترسی در بسته‌ها

سه لایه، هر سه لازم:

1. **برای دیدن فهرست پیوست‌ها، باید مجوز خواندن سند اصلی را داشت.**
2. **مواردی که کاربر مجاز به دریافتشان نیست اصلاً فهرست نمی‌شوند — نه اینکه قفل‌شده نمایش داده
   شوند.** نمایش «یک قرارداد هست که نمی‌توانی ببینی» خودش افشای وجود آن است. برای همین پروژه‌ای که
   برای مدیر اکانت ۱۸ پیوست دارد، برای فروش ۶ پیوست نشان می‌دهد.
3. **سرور به فهرست ارسالی کلاینت اعتماد نمی‌کند.** هنگام ساخت بسته، مجوز هر مورد دوباره بررسی
   می‌شود؛ موردی که کاربر مجاز نیست، بی‌صدا حذف می‌شود (پیام خطا هم افشاگر است). هر زیرسند با
   حذف‌های سطح‌فیلدِ همان کاربر تولید می‌شود، بنابراین بسته هرگز بیش از مجموع خروجی‌های تکیِ همان
   کاربر افشا نمی‌کند.

نمونه — همان پروژه، پیوست‌های ارائه‌شده به هر نقش:

| نقش | تعداد پیوست | آنچه نمی‌بیند |
|---|---|---|
| مدیر اکانت | ۱۸ | — |
| PMO | ۱۷ | فاکتور |
| حقوقی | ۱۷ | فاکتور |
| واحد اجرایی | ۱۶ | قرارداد، فاکتور |
| فروش | ۶ | سفارش کار، خروجی، QC، اصلاحیه، درخواست تغییر، فاکتور |

## فایل‌های پیوست

| نوع | رفتار |
|---|---|
| `application/pdf` | مستقیماً در بسته ادغام می‌شود |
| `image/png`، `image/jpeg` | در یک صفحه مستقل با عنوان فارسی درج می‌شود |
| سایر (Word، Excel، ZIP، ویدیو) | ادغام نمی‌شود؛ نام و دلیل آن در صفحه فهرست ثبت می‌شود |

تصاویر از همان مسیر HTML→PDF عبور می‌کنند (نه از `pdf-lib`)، چون قلم‌های استاندارد PDF فارسی را
رمزگذاری نمی‌کنند و عنوان فایل ناخوانا می‌شد.

## حسابرسی

هر بسته با `format: "pdf-bundle"` ثبت می‌شود، به‌همراه فهرست کامل بخش‌های درج‌شده، فایل‌های
درج‌نشده و بخش‌های حذف‌شده:

```sql
SELECT reason, after->'included', after->'notEmbedded'
FROM audit_events
WHERE action = 'EXPORT' AND after->>'format' = 'pdf-bundle'
ORDER BY "createdAt" DESC;
```

## محدودیت هم‌زمانی

رندر Chromium وابسته به CPU است، پس هم‌زمانی بیشتر «صف» می‌خرد نه توان بیشتر. اندازه‌گیری روی
دیتاست ۴۰۰ پروژه‌ای (docs/performance.md): از ۵ اتصال به بالا نرخ درخواست ثابت می‌ماند در حالی که
تأخیر خطی بالا می‌رود و RSS فرآیند بیش از دو برابر می‌شود.

- `PDF_MAX_CONCURRENCY` (پیش‌فرض ۲) — تعداد رندر هم‌زمان. هر رندر حدود ۱۵۰ مگابایت RSS می‌گیرد.
- `PDF_QUEUE_FACTOR` (پیش‌فرض ۴) — عمق صف به‌عنوان ضریبی از مورد بالا.

فراتر از `PDF_MAX_CONCURRENCY × PDF_QUEUE_FACTOR` درخواستِ در انتظار، پاسخ بلافاصله
`503 PDF_ENGINE_BUSY` است — به‌جای پیوستن به صفی که پیش از timeout کلاینت خالی نمی‌شود.

## امنیت رندر

Chromium با `--no-sandbox` اجرا می‌شود، چون کانتینر با کاربر بدون امتیاز و بدون `CAP_SYS_ADMIN`
اجرا می‌شود و sandbox setuid به آن نیاز دارد. سطح حمله با خودِ صفحه محدود شده است، نه با sandbox:

- context با `offline: true` ساخته می‌شود؛
- JavaScript غیرفعال است؛
- یک route filter هر درخواستی جز `data:` را abort می‌کند؛
- ورودی، HTML ساخته و escape‌شده توسط همین کدبیس است.

بازگرداندن قابلیت به کانتینر و اجرای Chromium با sandbox، پوسچر قوی‌تری است و یک تصمیم استقرار
محسوب می‌شود.
