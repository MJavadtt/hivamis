# Performance

Measured, not estimated. Every figure here comes from `pnpm bench` against a production build
(`node dist/server.js`, `NODE_ENV=production`) on the dataset described below.

```bash
pnpm --filter @hiva/api exec tsx prisma/generate-load-data.ts --scale=2 # double
```

## Harness

```bash

```


## What the rewrite changed

`/reports/executive` before, on the same dataset:

| | before | after |
|---|---:|---:|
| p95, sequential | 1,063ms | 38ms |
| p95, 10 concurrent | 7,200ms | 80ms |

It had been pulling every project, opportunity, invoice, cost declaration, task, change request,
risk, revision and feedback row into Node and reducing them in JavaScript, and `projectHealth` ran
a `tasks.filter()` per project — O(projects × tasks), about 8M comparisons per request at this
volume, on the CEO's landing page.

`/reports/units` went from 432ms to 27ms the same way: eleven numbers per unit that had been
computed by five `filter()` passes per unit over the full task, revision, QC, cost and work-order
arrays.

Two partial indexes (migration `20260909100000_report_rollup_indexes`) took the late-tasks
roll-up from a sequential scan of 20k rows to an index-only scan: **18.3ms → 1.9ms**. They are
partial because the queries filter `state NOT IN (...)`, a negation the planner cannot serve from
an ordinary index.

## PDF export

The most expensive operation in the system: Chromium, landscape, multi-page.

| conn | p50 | p97.5 | p99 | req/s |
|---:|---:|---:|---:|---:|
| 1 | 359ms | 385ms | 385ms | 3 |
| 5 | 797ms | 1,319ms | 1,320ms | 6 |
| 10 | 1,549ms | 2,422ms | 2,526ms | 6 |

Throughput is flat from 5 connections up — the work is CPU-bound in Chromium, so added
concurrency buys queueing rather than parallelism. That measurement was taken *before* the
concurrency limiter: process RSS went from 200MB to 496MB across the run and left 20 Chromium
helper processes alive.

With `PDF_MAX_CONCURRENCY=2` and `PDF_QUEUE_FACTOR=4` in place, the same run holds latency
comparable at 1 and 5 connections and, at 10, refuses 30 requests outright with
`503 PDF_ENGINE_BUSY` rather than letting a queue build that cannot drain before clients time
out. Helper processes during the run dropped from 20 to 9, and SIGTERM now reaps every one of
them — the browser was previously leaked on each restart because nothing called
`shutdownPdfEngine()`.

Deciding between the two behaviours is a capacity question, not a correctness one: raise the
limit alongside the container's memory, since each simultaneous render costs roughly 150MB.

## Revenue report at 2,000 projects (audit PERF-3)

`pnpm bench:revenue [projects]` (`bench/revenue.mts`) runs the real `revenueReport` on synthetic
records served by a stand-in for the database, so what it times is the calculation alone. Each project
has 8 tasks, 32 time entries, 3 invoices, 3 milestones and a payment; a quarter of them run media. The
report covers 12 months. Median of five runs after a warm-up, on the development laptop (Apple
silicon, Node 22):

| Projects | Before | After |
|---|---|---|
| 500 | 254 ms | 165 ms |
| 2,000 (16,000 tasks, 64,000 entries) | 1,187 ms | 679 ms |

**What changed.**

- Each position is worked out once per (project, instant) for a load. A month's end is the next
  month's start, and the last month ends now, which the project list reads again.
- Projects are looked up by id in a `Map` rather than by scanning the list for each of them.
- Closed periods are indexed by end and by name.

The growth was faster than linear before (×4.7 for ×4 projects) and is about linear now (×4.1).

**What remains.** The decimal arithmetic CALC-2 brought is the main cost now; it is the price of
exact money. Past several thousand projects, the next step would be computing month boundaries
incrementally per project.

## Bottleneck, and what is next

The remaining ceiling on the read endpoints is JSON serialisation, not the database:
`/reports/executive` returns ~139KB because `projectHealth` carries one row per open project.
At a few thousand projects that response is the cost. The fix, when it matters, is pagination or
a summary/detail split — a response-shape change, so not folded into a performance pass.

Three endpoints still hold unbounded `findMany` calls: `/reports/sales`, `/reports/sla` and
`/reports/data-quality`. They are fast today (8ms, 3ms, 11ms) because they read tables this
dataset does not inflate — opportunities, SLA clocks. They will degrade in proportion to those
tables and should be converted the same way before an organisation accumulates years of
opportunity history.
