## SEC-8 — demo accounts in production

- `server.ts` runs `demoAccountGate` before the reference sync, the jobs and the listener. With
  `NODE_ENV=production` and an active `@hiva.local` account it logs them at `fatal` and exits 1;
  `ALLOW_DEMO_ACCOUNTS=true` starts it, with a `fatal` line on every boot. A failed lookup does not
  refuse — the database being down is reported by everything after it.
- The way out needs no running API: `node dist/cli.js demo:deactivate` in a one-off container. It
  and `POST /users/:id/deactivate` share `deactivateUser`, which now writes its audit row (with
  before and after) in the deactivation's transaction; the route used to write it afterwards.
- The installer writes `SEED_DEMO_DATA=false` and `ALLOW_DEMO_ACCOUNTS=false`, refuses an
  administrator on `@hiva.local`, and so does `tenant:create` in production.
- Found on the way: `hivamis install` without `--domain` failed on macOS's bash 3.2 (an empty array
  is "unbound" under `set -u`). Fixed; the new test installs without a domain.

## SEC-2b — the tenant sweep

`apps/api/scripts/tenant-sweep.ts` walks the API's source with the TypeScript compiler and lists every
Prisma query on a model that belongs to an organisation whose `where` names none. Each such function
was read and given a verdict in `scripts/tenant-sweep.reviewed.ts`; `tests/039-tenant-sweep` fails on
a function nobody has reviewed and on a verdict whose function no longer has such a query.

### What the review found and fixed

Beyond contacts (SEC-1) and allocations (SEC-2), reading every function turned up these. Each one
let one organisation read or change another's records, or file a record against them.

| Where | What | Fix |
|---|---|---|
| `GET`/`PATCH /projects/:id/closure` | Read and wrote the closure checklist of any project by id | Project found in the caller's organisation first; the change is audited in its transaction |
| `POST /forms/submissions` (every form, bulk import included) | A form's record and person fields, and the submission's own links, were only checked to look like ids; a form's binding then wrote to that record (closure checklist, brief review, supplier rating) | Every `entityRef`/`user` field and link checked against the organisation: `422 UNKNOWN_REFERENCE` |
| `POST /forms/submissions/:id/decision` | Read the submission by id alone: an approver role in one organisation could decide another's form | Looked up in the decider's organisation |
| `POST /projects/:id/raci` | No project check: replaced any project's RACI matrix | Project and named people checked; audited in the transaction |
| `POST /feedbacks`, `POST /lessons-learned` | Ticked the closure checklist of any project named in the body | References checked first |
| `POST /invoices`, `/payments`, `/meetings`, `/qc-reviews`, `/activities`, `/proposals/:id/costs`, `/projects/:id/authorize` | Ids in the body written unchecked (an invoice could name another organisation's client and show it back; a failed QC review could raise a revision on another's deliverable) | `assertOwnReferences` on every one |
| `POST /delegations` | `fromUserId` not checked: authority could be lent from a user of another organisation | Source user found in the organisation |
| Messenger `handleUpdate` | A chat with no link was filed under the installation's first organisation | Filed under the linked person's, the sandbox caller's, or the link code's organisation; an unattributable chat on a several-organisation installation is answered and filed nowhere |
| `GET /projects/:id/360` | Read the first hundred SLA clocks of every organisation and filtered them here — could miss the project's own | The project's and its records' clocks asked for by id, in the organisation |

The isolation harness (P0-1) now sends the fields the stricter schemas require, so these routes' handlers
run in it; removing the RACI fix makes it fail with `added raci_assignments`.
